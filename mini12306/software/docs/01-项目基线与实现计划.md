## 1. 选题与背景

**选题**：Mini-12306 —— 简化版中国铁路 12306 在线车票服务系统。

**背景（来自项目需求原文）**

旅客乘火车出行需购买车票，某些情况下还需改签和退票。目前主要依靠车站售票厅：旅客需到售票厅查询车次、通过售票窗口购票/退票/改签。这种模式存在两个突出问题：

1. **购票、改签、退票难** —— 必须到售票厅排队办理，费时费力、效率低下，且无法快速应对旅行中的突发情况。
2. **无法及时获取车次及其变动信息** —— 车次/车票变动信息只能在售票厅获取或电话查询，实时性差、反馈慢。

**解决思路**：借助互联网技术，建设在线车票服务系统，集成第三方身份证认证、移动服务、银行在线服务等能力，让旅客在线完成查询、购票、退票、改签。

**开发平台与工具**

| 项 | 内容 |
| --- | --- |
| 智能开发平台 | **DeepSeek Harness（DSH）** |
| 主力大模型 | **deepseek-v4.1-flash** |
| 开发工具 | VS Code、Git、Node.js、pnpm、Postman/Apifox、Chrome DevTools |
| 文档工具 | Markdown + Mermaid，pandoc 导出 docx |

## 2. 技术选型

| 层 | 选型 | 理由 |
| --- | --- | --- |
| 前端 | React 18 + TypeScript + Vite | 组件化清晰、类型安全、启动快 |
| 样式 | Tailwind CSS | 原子化，设计规范易落地 |
| 路由/请求 | React Router 6 + TanStack Query | 标准方案；Query 自带轮询，适配支付状态查询 |
| 后端 | Node.js + Express + TypeScript | 与前端同语言，2 人组切换成本低，代码可读性好 |
| ORM | Prisma | schema 即文档，迁移可控 |
| 数据库 | SQLite | 零安装、单文件、便于演示与提交 |
| 校验/认证 | Zod + JWT + bcrypt | 入参校验 + 会话 + 加盐哈希 |
| 测试 | Vitest + Supertest | 单元与接口测试一体 |

**关于第三方服务**：需求要求集成身份证认证、移动服务（短信）、银行在线支付。本项目**不接真实接口**，改为实现 **Mock 适配层**——定义 `IdentityProvider` / `SmsProvider` / `PaymentProvider` 三个接口，本地提供 Mock 实现（含 Mock 银行收银台页面与异步回调），配置 `PROVIDER_MODE=mock|real` 一键切换。这样既保证功能完整可用，又保留了与真实服务同构的契约。

## 3. 项目范围

**做（In Scope）**

- 旅客端：注册、登录、实名认证、乘车人管理、车次查询、购票下单、在线支付、退票、改签、订单管理、公告查看
- 售票员端：窗口代客购票、按证件/订单号检索、代客退改
- 管理端：车站/车次/运行日维护、票价与定员维护、订单与用户管理、公告发布（含晚点、停运）、系统参数设置、审计日志、运营概览
- 基础服务：实名认证、短信、支付三类能力的适配层 + Mock 实现

**不做（Out of Scope）**

- ❌ 对接真实第三方接口（实名/短信/支付一律 Mock）
- ❌ 微服务、消息队列、Redis 集群等高阶架构（用单体分层 + SQLite）
- ❌ 原生 App 打包（"移动端"以响应式 Web + PWA 体现）
- ❌ 真实票价日历与递远递减算法（用可解释的简化票价模型）
- ❌ 候补购票、联程换乘、发票、保险、积分

## 7. 关键业务规则（基线摘要）

| 规则 | 取值 |
| --- | --- |
| 支付时限 | 下单后 **15 分钟**未支付自动取消并释放余票 |
| 单笔购票张数 | 1 ~ 5 张 |
| 乘车人上限 | 每账号 10 人 |
| 购票截止 | 开车前 **30 分钟** |
| 退票截止 | **开车后不可退票** |
| 改签次数 | 每张票**限改签一次**；开车后仅可改签当日车次 |
| 登录失败锁定 | 连续 5 次锁定 10 分钟 |
| 儿童票 / 学生票 | 儿童 50%、学生 75%（学生限二等座/硬座） |
| 余票显示 | ≥20 显示"有票"，1~19 显示数字，0 显示"无票" |
| 金额精度 | 一律以**分**为整数计算，禁止浮点 |
| 防超卖 | 数据库事务内**乐观锁 + 条件更新**，失败重试最多 3 次 |
| 幂等 | 下单、支付回调、退票必须支持幂等键 |

**退票费阶梯**（Δt = 开车时间 − 申请时间）

| 条件 | 费率 |
| --- | --- |
| Δt ≥ 8 天 | 免费 |
| 48 小时 ≤ Δt < 8 天 | 5% |
| 24 小时 ≤ Δt < 48 小时 | 10% |
| Δt < 24 小时 | 20% |

退票费向上取整到分，**最低 2 元**；退票金额 = 票面价 − 退票费。改签补收/退还**差价**，退差部分按上述阶梯对差额核收手续费。

**核心状态机（简版）**

```
订单：待支付 →(支付) 已支付 →(退票/改签) 部分退款/已退款/已改签
                 ↘(取消/超时) 已取消/已过期
车票：锁定 →(支付) 已出票 →(退票) 退款中 → 已退款 ／ →(改签) 已改签
```

## 10. 2 人分工与结对机制

**原则**：全员结对，不平行开发。**驾驶员（Driver）**操作键盘，**领航员（Navigator）**审查思路、查资料、记录问题；每 30 分钟左右互换一次，每阶段至少互换 3 次。

| 阶段 | 驾驶员 | 领航员 |
| --- | --- | --- |
| P0 立项 / P2 概要设计 / P4 编码①（后端） / P6 验收 | 成员甲 | 成员乙 |
| P1 需求 / P3 详细设计 / P5 编码②（前端与测试） | 成员乙 | 成员甲 |

**主责划分**：后端与数据模型以甲为主、乙参与；前端与交互以乙为主、甲参与；测试用例以乙为主；配置管理与发布以甲为主。两人均为全程参与者，上表只标"主责"。

**记录**：每次实验填写《结对编程日志》（角色、时段、任务、产出、卡点、解决方式），作为实验报告"过程记录"部分的原始素材。

## 11. AI 协作规范（DeepSeek Harness + deepseek-v4.1-flash）

**使用场景**：需求整理与文档起草、代码骨架与重复逻辑生成、单元测试用例生成、缺陷定位与解释、界面文案与排版建议。

**红线（必须遵守）**

1. AI 生成的代码必须**逐行看懂**才允许提交，看不懂的就问、就改，不许"能跑就行"。
2. 核心算法（余票扣减、退票费、改签差价、并发防护）**必须人工推导并写单元测试**，不得直接采信生成结果。
3. 实验报告与文档中须**如实标注**哪些内容使用了 AI 辅助。
4. 不得把真实身份证号、手机号、银行卡等个人信息投喂给模型；示例数据一律用虚构值。
5. 答辩时被问到的每一处实现，都必须能自己讲清楚原理。
